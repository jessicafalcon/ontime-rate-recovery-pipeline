# PROCESS.md — how it was built, and what kept it honest

One page for a reader who has seen the [README](../README.md) and wants to
know whether the numbers there can be trusted before running anything. The
short version: the work was done with an AI coding assistant, and the process
was designed so that the assistant's output had to pass machines it could not
argue with. The assistant proposes; the gate disposes.

## The loop

Every capability was one branch, one pull request, and one spec written from
[`specs/TEMPLATE.md`](../specs/TEMPLATE.md) before any code. A spec has four
sections that are not optional — Invariants, Evidence, Record updates, Threat
model — and exactly one DONE command whose output is the definition of done.
Invariants come first and are written as properties ("for every prompt whose
lookback has closed, the label is identical on every later run"), each paired
with the test that would falsify it; only then may a decision name a mechanism,
and only by reference to the invariant it satisfies. A spec that pins more than
about six decisions is split.

The order inside a branch was fixed: build against the spec, run the
deterministic gate, run the review agents, fix one finding per commit, repeat
until a round returns nothing, then the developer merges. Nothing reached the
remote before the developer had read the verdicts.

## What the machine checks

Three offline commands run on every branch, in this order, before any reviewer
reads a line. None needs a service or a network.

- **`make review-gate`** — the test suite, a read-only lint, the docs guard,
  and the spec's own contract: every test id and `make` target its Evidence
  table names must exist, every record file on its Record-updates list must be
  in the branch's diff, every symbol it says it deleted must be gone from the
  tracked tree, and any change under `fixtures/` fails unless the spec declares
  a `Freeze:` line (`check_fixtures`, `freeze_declarations`).
- **`make mutate`** — the mutation sweep. The unmutated suite runs first in a
  throwaway worktree and must be green. Then each line of the spec's
  `mutations` block breaks one guard on purpose — delete the call, return a
  constant, invert the guard, swap a sort key, or drop or swap one arm of a SQL
  `case` (`OPERATORS`, `SQL_OPERATORS`) — and the suite must go red. A
  mutation that survives is a correctness finding: a guard nothing tests.
- **`make check-docs`** — every relative link resolves, every `make` target a
  living document names exists, every guard a document cites by name exists
  in source as an exact token, the open BACKLOG count in the operating manual
  equals the un-struck rows, and every position in a tracked record where a
  project or account identifier could sit holds a placeholder shape.

## What holds the data still

The pipeline's numbers are only worth pinning if the inputs cannot move under
them.

- **A frozen fixture.** `fixtures/tiny/` — raw events, dimensions, truth and
  the expected outputs — is read-only after the branch that froze it. Only
  `make freeze` writes it, it refuses without command-line `CONFIRM=yes`, and
  the review gate fails any change to a fixture unless the spec declares the
  re-freeze (a `Freeze:` line); `make freeze` itself also refuses without a
  DECISIONS entry saying why. The generator's own writer refuses
  the directory outright (`FixtureWriteRefused`); a content manifest
  (`MANIFEST.sha256`) makes drift a red line on every load.
- **Pins, not prose.** Every number a reader sees lives once, in
  `tests/pins.py`, read off the first green build. A drift is a red test,
  never a rewritten constant. The README's headline and table, the findings
  chart, the simulation blocks in `docs/RESULTS.md` and the power table in
  `docs/AB_DESIGN.md` are generated from those pins into marker-confined blocks
  (`make readme`, `make simulate`, `make power`) and regenerated byte-for-byte
  under `make test`. The one essay that types its figures by hand,
  [`docs/INSIGHT.md`](INSIGHT.md), has a test asserting each figure equals its
  pin and that no unpinned figure has crept in.
- **Truth isolation.** The generator's assigned causes are a side-file only
  `eval/` reads. A structural test greps every pipeline directory for the word;
  the directory list is derived from the tree (`pipeline_dirs`), so a new
  package is guarded the day it appears, and a positive control proves the
  grep finds a planted reference.
- **Determinism.** Same seed, same bytes: counter ids, a fixed simulation
  start, no wall clock on the data path, every comparison sorted by a declared
  key. Anything non-deterministic by nature — run ids, timings, cloud job ids —
  is carved out by name and nothing asserted reads it.

## The reviewers

Four read-only agents, none able to edit: a code reviewer (the contracts in
[CLAUDE.md](../CLAUDE.md)), a functionality tester (runs the DONE command and
the negative cases, reports coverage gaps), a security reviewer (credentials,
IAM, destructive targets), and a coherence auditor (whole-repo drift between
code and records, mandatory at every exit). Which ones run is a lookup on the
files a branch touched, not a judgment. When any agent returns a finding, the
session stops: the developer reads the finding and the proposed fix before
anything changes.

Two rules came from being burned. First, **one correctness fix per commit**,
with the invariant it restores in the message: three early rounds landed
24, 21 and 15 findings in one commit each, and each following round found
bugs inside the previous round's fixes. Second, **the review cap**: when two
consecutive rounds report findings only in the previous round's fixes, patching
stops, the invariant is written down, and the mechanism is re-implemented once
against it. The first time the cap fired, the fix that had been failing was a
longer denylist at a boundary the repo does not own; the re-implementation
replaced it with an allowlist over a closed set, pinned exactly by a test, and
that became a standing contract.

## What the assistant did, and what it did not

The assistant drafted the specs, the code, the tests, the records and this
page; ran the gates; spawned the agents; wrote the fix commits. The developer
approved every spec before implementation, read every finding and every
proposed fix, decided each re-freeze and each dependency, authorised every
cloud spend individually, and merged every pull request. Where the assistant
was wrong, the record says so: the tiny fixture's cohort anchor lands on a
bin tie and its simulated lift is negative; a headline once added a fourth
hand-typed label on the very edit a BACKLOG trigger was waiting for; a fake
once bypassed the mapping it was meant to test and the suite stayed green. Each
of those is a DECISIONS entry, a BACKLOG row with a trigger, or a test that
would now catch it — that is the point of the loop.

## Where the trail is

[DECISIONS.md](../DECISIONS.md) is the why-not-X log, one entry per non-obvious
choice, superseded entries annotated in place and never deleted.
[BACKLOG.md](../BACKLOG.md) holds every deferred finding with a revisit trigger;
a row is done or re-deferred at every exit, never dropped. [PHASES.md](PHASES.md)
is the step-by-step record with each step's one-line Done-when.
[CLAUDE.md](../CLAUDE.md) is the operating manual all of the above enforce.
