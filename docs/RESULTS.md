# RESULTS.md — the counterfactual simulation

What the pipeline reports (ARCHITECTURE §7): (a) label accuracy vs truth
(`make eval`), (b) reachable-centre MAE (`make eval`), and (c) — this file —
the simulated on-time rate under the recommended schedule vs baseline. It
is a **counterfactual simulation, not an A/B**: outcomes are re-drawn from
the same latent that generated the data, with the generator's own response
rule (`generator/response.py::open_probability`). It shows that the served
schedule scores well under the rule the data came from; it says nothing
about real users. The production experiment is `AB_DESIGN.md`.

Each block below is GENERATED by `make simulate PROFILE=<p>` (check mode
diffs it byte-for-byte and exits 1 on drift; `WRITE=yes` rewrites it) —
never edit inside the markers. The seed is `tests/pins.py::SIMULATE_SEED`;
`medium` is seeded and unfrozen, so its block regenerates from
`data/out/medium/`.

## How to read a block

- **Rows.** `data` = the built `attribution` label counts (the pipeline's
  output on the data; equal to truth at accuracy 1.000). The three arms
  re-draw every prompt under a schedule: `baseline` = the hour each prompt
  was actually sent at; `cohort` = the cohort band anchor
  (`scores_send_time.cohort_hour_local`, no per-user shift); `recommended`
  = the served `send_hour_local:send_minute_local`.
- **Common random numbers.** All three arms share four uniforms per prompt,
  applied in the generator's order (delivery → skew → respond → upload). So
  `delivery_fault` and `unattributed` are identical across arms by
  construction, `timing_gap` is the only cause the schedule moves, and
  `upload_fault` moves only through the number of responders (its rate
  among responders and its lateness are never simulated — no time quantity
  is drawn). The simulated `baseline` differs from `data` by draw noise
  only; the lift is `recommended − baseline`, apples to apples.
- **Columns.** The five labels (`METRICS.md`), `prompts_sent`,
  `prompts_delivered = prompts_sent − delivery_fault` and `ontime_rate =
  on_time / prompts_delivered` (the METRICS denominator).

# The temporal holdout — the non-circular counterpart

The simulation above re-draws every outcome from the same latent that generated
the data (it reads `truth/`). That proves the served schedule scores well *under
the rule the data came from* — it cannot prove the schedule tracks behaviour the
model never saw. The temporal holdout (ARCHITECTURE §7 report (d)) is the
non-circular counterpart: it reads only observed behaviour off the warehouse.

The pipeline serves a schedule on data landed with an **upload-date cut**
(`make dbt-build … THROUGH=<upload-date>`), then scores that served schedule
against the RAW organic `app_opened` opens **uploaded after the cut** — the
reachability signals the model did not see at serving time. Because organic opens
upload promptly, "uploaded after the cut" is essentially "opens that happened
after the cut": a genuine train-past / score-future split (the 72 h late-arrival
tail is why the cut is on *upload* date, not simulation day — `THROUGH` selects
files by upload date). It reports two measures for each arm — the served per-user
hour (`recommended`) and the cohort band anchor (`cohort`):

- **`in_window_share`** — the share of held-out opens whose local hour is within
  ±1 h of the served hour (higher is better: the served time lands near real
  activity).
- **`mean_nearest_hours`** — the mean over users of the circular distance from
  the served hour to that user's nearest held-out open (lower is better).

Each block is GENERATED by `make holdout PROFILE=<p>` (check mode diffs it
byte-for-byte, `WRITE=yes` rewrites it) — never edit inside the markers. It reads
no truth and no clock; the cut and the window are `tests/pins.py::HOLDOUT_CUTS`
and `HOLDOUT_WINDOW_HOURS`.

### Incremental re-run is NOT cheaper here — the item-6 case, measured

A second build with no `--full-refresh` (incremental) scanned **19.45 GB** —
*more* than the full build, not less: `stg_events` 3.672 GB, `stg_prompts`
3.557 GB, above their full-build scans. The cause is measured, not guessed:
**`raw.events` has no partitioning** (`timePartitioning: None`), so the
incremental models' lookback filter on `server_upload_time` cannot prune the
SOURCE scan — every run re-reads all of raw, and BigQuery's dynamic
`insert_overwrite` adds a merge on top. The OUTPUT tables are partitioned and do
prune (below); only the raw scan is unpruned.

This is exactly the workload ROADMAP item 5 was meant to produce for item 6
(`fix/append-landing`): make raw append-only and partitioned by upload date, so
`THROUGH` becomes a partition predicate and the lookback filter prunes the raw
scan from ~3.6 GB (full) to a window. The amendment for item 6 is now backed by
a measured number, not a guess.

**Fixed in `fix/append-landing` (landed 2026-09-03).** `raw.events` is now
DAY-partitioned on `server_upload_time` (a `WRITE_TRUNCATE` load per
`raw.events$YYYYMMDD`), and `stg_events` bounds its source read to a superset
upload-time window (`server_upload_time ≥ max(server_upload_time) −
(lookback_days + margin) days`) inside `is_incremental()` and `target.type ==
'bigquery'` — so the incremental re-run scans a window of partitions instead of
all of raw. DuckDB is untouched (no partitions, no benefit) and every DuckDB
golden is byte-identical.

**Live BigQuery parity, run 2026-09-03 (ask-first, cents).** On a clean warehouse
`make test-int-bigquery` read the three goldens back from BigQuery byte-for-byte
and re-asserted the pins — confirming the **gzip landing, DAY-partitioned
per-partition load, and FULL-build** output are byte-identical to DuckDB (`4 passed`).
(A fresh decorator load self-created the DAY-partitioned `raw.events`; a
pre-existing non-partitioned table must be dropped once — `docs/DEPLOYMENT.md`.)

**The incremental source-scan prune, proven live (fix/prune-live-proof, run
2026-09-03, `6 passed`, ~20 min, cents).** The harness now adds an incremental
parity phase: reset `raw.events` clean, land ≤ a cut and FULL-build (the closed
state), land the late tail and run a **PLAIN** build — so `is_incremental()` is
true, the source-scan prune predicate renders and **executes on BigQuery**, and
the built tables converge **byte-identical** to the frozen full-scan goldens
(`test_incremental_build_matches_frozen`); the compiled `stg_events` carries the
`timestamp_sub` source predicate, proving the guard held live
(`test_incremental_prune_predicate_rendered`). The prune's live **correctness /
byte-parity** is thus proven, not only offline. One honest limit: tiny's raw
spans 9 days, inside the 10-day prune window (`lookback_days + margin`), so the
predicate excludes **no** partition here — the byte **reduction** is a
>10-day-span effect. Its magnitude is the large-profile number: raw was
un-partitioned there, forcing the 19.45 GB re-scan above; a large **incremental**
re-run on the now-partitioned raw would measure the reduced window scan (a
hand-recorded follow-up, non-deterministic — not a pin).
